# B-3 — ccu-mqtt node fixes and additions

**✅ done 2026-09-04** (`4.3.0`) — issues #115, #22, #167, plus the three
findings from ROADMAP §8.2 that the hm2mqtt 3.0 rewrite had confirmed.

## Fixed

- **The writeable check never fired.** Both `putParam` and `putParamset`
  tested `!(description.OPERATIONS) && 2`, which is `(!OPERATIONS) && 2` —
  always falsy, since `OPERATIONS` is a non-zero number for every real
  parameter. Read-only parameters were written regardless. Now
  `!(OPERATIONS & 2)`, and the write is skipped.
- **`putParamset` cast against the wrong description.** It passed
  `paramsetDescription[filter.param]` for every parameter; `filter.param`
  only exists on the `putParam` topic, so it was `undefined` there and
  the whole paramset went out uncast (strings where the CCU wanted
  numbers or booleans). Each value is cast against its own description.
- **Enum names never worked.** The CCU returns them in `VALUE_LIST`, but
  `lib/cast.js` and `lib/message.js` read `ENUM`, which no interface
  process sends: all 9494 ENUM-typed datapoints in the shipped
  `paramsets.json` carry `VALUE_LIST` and none carries `ENUM`. So
  `msg.datapointEnum` and `msg.valueEnum` had always been `undefined`,
  and writing e.g. `AUTO-MODE` to an enum datapoint fell through to the
  numeric cast and produced `0`. `enumList()` reads `VALUE_LIST` with
  `ENUM` as a fallback for hand-written data.
- **The divergent cast copy is gone.** `ccu-mqtt.paramCast` differed from
  `lib/cast.js` only in clamping to MIN/MAX (and in producing `NaN` for
  unparseable input, which XML-RPC cannot encode). `castValue` gained a
  `clamp` option; the mqtt node passes it, the value nodes do not (#74).
- The empty-name topic bug (`hm/status//STATE` for channels without a
  ReGa name) was already fixed in 4.2.0.

## Added

- **`get`** (#115): `hm/get/<channel>/<datapoint>` republishes the last
  known value on its status topic. An empty datapoint republishes every
  datapoint of the channel. Fresh user interest in April 2026.
- **`rpc`** (#22): the topic was already in the dispatcher's table, but
  the class had no `rpc()` method, so `typeof this[command] === 'function'`
  was false and the message was silently dropped; `topicOutputRpc` was
  never read at all. That is why both fields sat commented out in the
  editor since 2018 — exposing them would have created two settings that
  do nothing. Both are visible now; the result or the error is published
  on the response topic, and the never-working default topic loses its
  meaningless `${command}` segment (migrated on dialog open). An empty
  topic disables a command.
- **#167**: `getRegaData()` (channel names, rooms, functions, groups) ran
  once, in the connection constructor; the recurring poll only refreshed
  variables and programs. A function added in the CCU WebUI was therefore
  invisible until the flow was redeployed. New connection option
  _names/rooms refresh_ (minutes, default 15, 0 = off) re-reads channel
  names, rooms and functions from the ReGa poll's tail.

`resolveChannel()` now holds the channel-name/address resolution the four
command handlers each had inline.
