# B-2 — Dynamic node configuration via msg

**✅ done 2026-09-04** (`4.3.0`) — issues #172, #71, #103, #80, #56,
#148, #185, #133.

The request arrived from every direction and was deliberately designed
once rather than patched per node (which is why PR #173's auto-subscribe
was closed rather than merged).

## The mechanism

`msg.config` is an object whose properties override the receiving node's
own configuration **for that message only**. `nodes/lib/dynconfig.js`
builds the effective configuration; the stored one is never touched.

Why a namespace rather than flat properties everywhere: an event message
already carries `channel`, `datapoint`, `deviceType`, `rooms` and friends,
so honouring those on the signal or display node would let any message
coming from an event node silently retarget it. `msg.ccu` was the obvious
namespace but is taken — it holds the CCU host name — hence `msg.config`.

Each node passes the list of keys it accepts; anything else in
`msg.config` is ignored, so a stray property cannot reach node internals.
The flat mechanism the value/get-value/set-value nodes always had (fill in
fields left empty in the dialog from `msg.channel`, `msg.rooms`, …) is
unchanged and keeps working; `msg.config` wins over it.

## Per node

- **set-value** — the whole filter plus `force`. This is also the fix for
  #133: `setValues()` wrote message properties into `this.config`, so the
  `if (!config[key])` guard skipped every later message and the node
  stayed pinned to the first message's targets. The whitelist/blacklist
  are keyed by the effective filter now, so an unchanged filter keeps the
  caching benefit and a changed one is re-evaluated. The 200-line inline
  matching chain moved to `nodes/lib/channelfilter.js` (pure, 14 tests),
  which also fixed the device-name filter requiring the _channel_ to have
  a ReGa name while comparing the _device_ name.
- **value** — `iface`, `channel`, `datapoint`. A message without a
  payload writes nothing (the 4.0.0 guard) and now retargets the output
  subscription, which is what #172 asked for. For a node with its own
  channel/datapoint configured this is a no-op unless `msg.config`
  overrides them, so no existing flow changes behaviour.
- **switch** — the source selection (`iface`/`channel`/`datapoint`/
  `datapointProperty`/`sysvar`/`sysvarProperty`), so one node serves a
  whole subflow (#103).
- **sysvar** — `name`, plus a typed input for _where the value comes
  from_ (msg/flow/global/env) instead of always `msg.payload` (#56).
- **signal** — every command field including `soundList`/`dimmerList`,
  which also accept a plain array of values instead of the editor's
  list-of-objects shape (#148). The existing `<field>Type` typed inputs
  keep working; `msg.config` wins over them.
- **display** — channel and the EP-WM55 settings, joining the lines,
  colours and icons that were already overridable.

## Subflows (#158)

Node-RED substitutes `${PARAMETER}` in a node's string properties before
the node is constructed, so subflow parameters already worked at runtime —
but the editor's channel autocomplete cleared any value that was not a
known channel address, wiping the placeholder every time the dialog was
opened. Fixed in the value, get-value, switch, signal and alexa editors.

Not done: an explicit `env` type on the filter fields of the event nodes.
The `${PARAMETER}` route covers the use case and the filters are read once
at construction, so a typed input would need runtime evaluation for little
gain. Revisit if someone asks.
