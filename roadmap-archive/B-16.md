# B-16 — ccu-homeassistant: Home Assistant MQTT auto-discovery node

**✅ done 2026-09-04** (released as 4.2.0) — user request 2026-09-04.

New node `ccu-homeassistant`: publishes device-based Home Assistant MQTT
discovery configs (HA ≥ 2024.11) for a checkbox-selected set of devices.
Companion to a ccu-mqtt node whose topic templates and payload format it
reuses, so state and commands keep flowing through ccu-mqtt and the node
itself only emits the retained discovery configs (plus the aggregate
`<channel>/PRESS` item for event entities); unticked devices get an empty
retained config. Mapping ported from hm2mqtt.js (`lib/haroles.js`,
`lib/hadiscovery.js`, channel TYPE as primary role key because only about
half of the shipped VALUES descriptions carry CONTROL hints). Editor: device
table modeled on RedMatic-HomeKit (filter, check/uncheck all), ccu-mqtt
select, prefix, generic-entities option; `type=devices` admin endpoint.
Rode along: ccu-mqtt HA command words (OPEN/CLOSE/STOP/ON/OFF, HM
`*-MODE`), empty-name topic fix, connection `deregister` fix.

Verified 2026-09-04 on the two lab CCUs against Home Assistant 2026.9.0
(docker) and she 1.51.1 (the author's dev instance on the test broker plus
a private instance): DRS8 switches with round trip, DRI16 inputs + events,
DRAP sensors, PDT light with brightness (plain payloads), WRC2 events,
removal on untick, editor smoke test by the user. Three payload defects
found only through the live test (availability-list `val_tpl`, switch
`stat_on`/`stat_off`, binary-only device classes on sensors) — the first
two are inherited from hm2mqtt.js / mqtt-interfaces-core and should be
fixed upstream. Not covered by lab hardware: cover and climate payloads
(unit tests only), real key presses. Known gaps (as upstream): RGBW lights,
sirens, garage doors, sysvars/programs as entities.

Original item: | B-16 | **New node `ccu-homeassistant`: Home Assistant MQTT auto-discovery for a checkbox-selected set of devices** (decided 2026-09-04: a dedicated node, not an option on ccu-mqtt). It is a companion to an existing ccu-mqtt node, not a replacement: its config references one ccu-mqtt node of the flow (select populated via `RED.nodes.eachNode`, type `ccu-mqtt`, same ccu-connection) and **reuses that node's configured topics** — `topicOutputEvent` as HA state topics, `topicInputSetValue` as command topics, `topicOutputSysvar` for sysvars later — plus its payload format (`payloadOutput` mqsh-basic/extended/plain → matching `value_template`, e.g. `{{ value_json.val }}`). State and commands keep flowing through ccu-mqtt; the new node only emits the retained discovery configs `{topic, payload, retain: true}` for the same downstream mqtt-out node (no broker connection of its own), republishes them on deploy/reconnect, and publishes empty retained configs for devices that were unchecked (removal from HA). **Device selection like RedMatic-HomeKit's `redmatic-homekit-homematic-devices` node**: the config dialog loads all devices of the connection from the `/ccu` admin endpoint into a table (checkbox · name · address · type, "enable all"/"disable all" buttons, filter box, optionally expandable per-channel rows), stored as a `devices` object keyed by address — but **opt-in**: nothing is checked, hence nothing published, until the user ticks a device. Mapping modeled on hm2mqtt.js [`lib/hadiscovery.js`](https://github.com/hobbyquaker/hm2mqtt.js/blob/master/lib/hadiscovery.js) (README section "Home Assistant"): one HA device per Homematic device, device-based discovery payloads `homeassistant/device/<id>/config` (HA ≥ 2024.11; prefix configurable), entities derived from the paramset descriptions' `CONTROL` hints — switch (SWITCH.STATE, HmIP virtual receivers), light (dimmers), cover (blind position/tilt/direction), climate (HM/HmIP thermostats, modes/presets), binary_sensor (contact/motion/presence/smoke/water), event (key press short/long), lock (KEYMATIC), sensor (energy, weather, maintenance) — port hm2mqtt's mapping table rather than re-deriving it. **Constraint found 2026-09-04 (corrected the same day):** only 290 of the 647 VALUES entries in the shipped `paramsets.json` carry `CONTROL` hints (the older contributed user dumps were stripped of them), and the persisted runtime cache of existing installs inherits that — so a pure CONTROL-based mapping would silently skip roughly half the device types. Key the mapping on the channel `TYPE` from the device metadata (always present) and use CONTROL only as a refinement where the cache has it (live fetches and the B-1 regen bring CONTROL in; the fetch tool stores the full response). B-3 is not a prerequisite (HA commands use the setValue path, which casts in the connection), but its trivial fixes ride along. Builds on Phase 3's extracted `lib/topic.js` so the HA node computes exactly ccu-mqtt's topics. **Runs on branch `b-16-homeassistant`, target 4.2.0** (decided 2026-09-04; 4.1.0 stays the small data release). **Status 2026-09-04: implemented on the branch** — `nodes/lib/haroles.js` + `nodes/lib/hadiscovery.js` (pure, 24 unit tests on paramsets.json fixtures), `nodes/ccu-homeassistant.{js,html}` (device table, ccu-mqtt reference, republish on input, removal configs), `type=devices` admin endpoint, ccu-mqtt command words (OPEN/CLOSE/STOP/ON/OFF, HM `*-MODE`) + empty-name topic fix + connection `deregister` fix, README section, `examples/home-assistant.json`, CHANGELOG "Unreleased (4.2.0)". **Verified end-to-end 2026-09-04** on the lab CCU3 (RedMatic 9.0.0-alpha, aedes broker inside Node-RED) against Home Assistant 2026.9.0 (docker): HmIPW-DRS8 → 8 switches (state from the transmitter channel, secondaries disabled), HmIPW-DRI16 → 16 opening sensors + 16 event entities, HmIPW-DRAP → bus voltage/current sensors; switch round trip HA → `hm/set` → CCU → `hm/status` → HA state on/off; untick + deploy removes the device from HA. Three payload defects found and fixed only because of the live test (HA rejected/ignored silently): an availability-list entry takes `val_tpl`, not `avty_tpl`; a switch needs explicit `stat_on`/`stat_off` because HA compares the templated state with the command payloads by default; a sensor/number must not carry a binary_sensor class (`running` on the ENUM datapoint PROCESS). The first two are inherited from hm2mqtt.js / mqtt-interfaces-core and should be fixed upstream too. Also fixed: the readiness wait treated an empty VALUES paramset as "not cached" (5-minute fallback delay). Second round on the OpenCCU lab box (same HA, second ccu-mqtt with prefix `hm2/` and **plain payloads**, so the non-JSON templates are covered too): HmIP-PDT → light with brightness (HA brightness 128 → `LEVEL` 0.5 → state on/128 from the DIMMER_TRANSMITTER channel, off → 0, plain on → last brightness), HmIP-WRC2 → 2 event entities + battery sensor, no HA warnings. **Second consumer:** [she](https://github.com/hobbyquaker/she) 1.51.1 (the author's dev instance on the test broker, which both lab flows now feed as well) parses the same retained payloads (`GET /she/mqtt/ha-discovery`) into the 5 lab devices with plausible entity groups and no orphaned/duplicate flags — she is the lighter, scriptable check for future B-16 changes; HA stays the reference for schema validation. Not covered by the lab: cover and climate payloads (no blind or thermostat paired anywhere), key presses on real hardware. **Open before merge:** editor smoke test in a browser (device table, ccu-mqtt select), CI run (the local mocha suite cannot bind port 8181 under WSL); cover/climate stay unit-test-only until a device is available. Merge after 4.1.0 ships. Known gaps upstream too: RGBW lights, sirens, garage doors, sysvars/programs as entities. | user request |
