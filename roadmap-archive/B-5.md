# B-5 — Ping checks, sysvar node properties and status

**✅ done 2026-09-04** (`4.3.0`) — issues #44, #54, #52, #124, #166, #96,
#56, #183.

A collection of small connection- and node-level items that had all been
open since 2019/2020.

- **#44 — configurable ping checks.** The connection node had a _ping
  timeout_ field but no way to switch the check off: entering 0 fell
  through `Number.parseInt(config.rpcPingTimeout, 10) || 60` back to 60
  seconds. New _RPC ping_ checkbox (default on). Off means no periodic
  ping and no timeout-triggered re-init for that connection — the honest
  reading of "deactivate ping checks", with the consequence documented in
  the dialog.
- **#54 / #52 — last value and its age under the node.** The connection
  keeps `value`, `ts` and `lc` for every datapoint and system variable;
  the nodes simply never showed them, and the sysvar node showed nothing
  at all unless "emit value on start" was enabled.
  `nodes/lib/valuestatus.js` renders `<value> (3m)` and re-renders on a timer whose
  interval follows the resolution shown, so the line does not go stale
  between events. Used by the sysvar node (which also seeds it from the
  connection's cache when "emit value on start" is off) and the rpc-event
  node (which shows the topic that last fired).
- **#96 — filter uncertain values.** The `uncertain` flag was already in
  every message; there was no way to filter on it. `uncertain` is a
  subscription filter property now, exposed as a _discard uncertain
  values_ checkbox on the value and rpc-event nodes. It is only put into
  the filter when the option is on, so existing subscriptions are
  unaffected, and it is evaluated before `callCallback()`'s attribute
  loop, which may break early for a whitelisted datapoint.
- **#166 — immediate sysvar echo lost under concurrency.** `setVariable()`
  triggers a ReGa poll so the new value comes back without waiting for
  the 30 s interval, but only `if (!this.regaPollPending)`, and
  `regaPoll()` itself no-ops while one is in flight. Writing several
  variables at once therefore left all but the first invisible for up to
  a poll interval — exactly the reported symptom ("works for one
  variable, not for several"). The request is remembered and exactly one
  more poll runs when the current one finishes.
- **#183 — RSSI conversion guarded.** `dp.value -= 256` ran for every
  RSSI_DEVICE/RSSI_PEER value from the ReGa poll, so a value that was
  already signed, or the 0 that means "never received", became -318 or
  -256. Now only for values above 127, matching hm2mqtt's guard. (The
  XML-RPC event path needs no conversion.)
- **#124 — re-read variable descriptions on poll** was already fixed in
  2020 (commit 453f2b2, v3.2.1) and the issue merely never closed; the
  remaining gap (`info` not selectable as a property) is noted below.
- **#56** — the sysvar node's configurable source property landed with
  B-2, which owns the dialog change.

## Not done

- `info` (a variable's description) is still not selectable as a single
  property in the get-value/sysvar nodes; it is reachable through the
  whole message. Left for whoever touches those property lists next.
