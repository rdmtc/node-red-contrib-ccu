Scope: ROADMAP §7 B-1 / OQ-5. Research only — nothing in the repo was
modified, the live CCU was only read.

## 1. How paramsets.json is built today

**Format.** `paramsets.json` (repo root, 9.7 MB, 2222 keys) is exactly the
runtime paramsetDescription cache that `nodes/ccu-connection.js` writes to
`<userDir>/paramsets.json`. Flat object, key =

    <iface>/<device TYPE>/<device FIRMWARE>/<device VERSION>/<channel TYPE>/<paramset>

built by `paramsetName()` (ccu-connection.js:1934, join of
`[iface, d.TYPE, d.FIRMWARE, d.VERSION, cType, paramset]`). `cType` is empty
for device-level paramsets (`…/2//MASTER`). `VERSION` is the integer device
description version (HmIP: 65536 = 1.0.0, 131072 = 2.0.0). Paramset names
seen: MASTER, VALUES, LINK, SERVICE. Value = verbatim `getParamsetDescription`
result: `{PARAM: {MIN, MAX, DEFAULT, TYPE, OPERATIONS, FLAGS, ID, UNIT?,
CONTROL?, ENUM?…}}`. So MIN/MAX/VERSION all live inside the key/values exactly
as the CCU serves them over XML-RPC.

**Role at runtime.** The shipped file only *seeds* the user's cache on first
start (`loadParamsets()`, ccu-connection.js:915). Any key not in the cache is
fetched live from the user's own CCU (`paramsetQueue*`, throttled 200 ms) and
persisted. Because the key contains the device firmware version, a device on
new firmware gets a fresh fetch; a *stale value under an unchanged key* is
never refreshed — that is the only way shipped data can go wrong (there is no
invalidation).

**tools/paramsets-join.js** (18 lines, excluded from linting): merges a second
file hard-named `ccu_paramsets_v2.json` (repo root, not in git) into
`paramsets.json` via `obj-ease` `extend` (second file wins on conflicts) and
rewrites `paramsets.json`. `obj-ease` is not in package.json anymore — the
script no longer runs as-is.

**History.** `git log --follow paramsets.json`: seeded 2018 ("ship prebuild
paramset file", 078d53e), then grown 2019–2020 by merging *contributed runtime
caches* from users/other installations ("update/extend paramsets" — 8324b26,
c8d2f39, 7705014, 1f24fc3, 0b24e97, 511a319). Last extension Oct 2020; that is
why everything HmIP after ~2020 (FBL, BBL>1.6.2, DRBLI4, BSL v2, WRCD, ESI,
BROLL-2, eTRV-3/E…) is missing.

`tools/get-channels-working.js` is only an analysis helper (lists channel
types that have WORKING/PROCESS datapoints); no pipeline role.

## 2. Source evaluation

### 2a. CCU3 firmware image (3.89.8, rootfs.ext4)

Extracted with p7zip (`7z x rootfs.ext4 <paths>` works fine on macOS; the
image was already gunzipped in the hm2mqtt scratchpad). Copies under
`scratchpad/b1/`:

- `rootfs/firmware/rftypes/` — 128 XML files: **complete BidCos-RF device
  definitions** incl. parameter physical/logical types, min/max, conversions.
  Parseable offline, but the format is rfd's internal one; producing the exact
  XML-RPC description (OPERATIONS/FLAGS ints, computed MIN/MAX after
  conversion) needs a re-implementation of rfd's mapping. Feasible, medium
  effort, only worth it if full BidCos type coverage without devices is ever
  needed. Same 128 files exist on the live CCU at `/firmware/rftypes`.
- `rootfs/opt/HMServer/HMIPServer.jar` + extracted
  `hmip-devicedescription/` — HmIP catalog:
  `devicespecification/eQ-3/device_*.xml` (device → channel types, all ~500
  devices incl. every issue device) and
  `channelspecification/channel_type_*.xml` (parameter *names* per channel).
  **MIN/MAX/TYPE/OPERATIONS are NOT in the XMLs** — they are generated by
  compiled Java (`channelspecification/*Factory.class`,
  `stateparameter/*.class`). Offline generation of HmIP paramset descriptions
  would mean decompiling/reimplementing eQ-3 code — **not viable**.
- `rootfs/opt/HmIP/legacy-parameter-definition.config` — only CONTROL/UNIT
  cosmetics for the legacy XML-RPC API, no MIN/MAX.
- CuxD: not in the firmware at all (third-party addon, jens-maus/cuxd).

**Verdict 2a:** firmware image is excellent for *knowing what exists*
(device → channel → parameter names, e.g. to verify an issue) but cannot
produce paramsets.json entries for HmIP. Keep it as a reference/verification
source only.

### 2b. Live CCU (recommended route)

`ssh root@homematic-ccu3` works (fw **3.87.6**, idle, image is 3.89.8 —
decision 2026-09-04: the production CCU stays on 3.87.6; the regen runs
against it as-is. Two lab CCUs on 3.89.8 — x86_64 OpenCCU and an armv7l
CCU3 — exist for tests but have few/no devices paired).
`/etc/config/InterfacesList.xml`: BidCos-RF (ext. port 2001, internal 32001),
VirtualDevices (9292/32992? → internal `http://127.0.0.1:39292/groups`),
HmIP-RF (2010/32010), BidCos-Wired (2000/32000). No CUxD installed.
XML-RPC `listDevices`/`getParamsetDescription` verified working from the CCU
shell via wget POST (responses ISO-8859-1; `homematic-xmlrpc` — already a
dependency — handles that).

Live fetch produces byte-identical structures to what the runtime caches —
same code path the file has always been filled from. It only covers *paired*
device types + group types, but that is how the file was always grown
(merged contributions, never pruned), and the runtime self-heals gaps for any
user's own devices. Inventory of this CCU (saved in
`b1/live-listdevices.xml`): 57 HmIP types incl. HmIP-FBL (fw 1.8.12),
HmIP-BSL (fw 1.0.2), HMIP-eTRV/eTRV-2/-B/-B1/-B-2/-C/-C-2, MP3P, BROLL(?);
30 BidCos types; HmIP-HEATING group now FIRMWARE 2.0.0 / VERSION 131072
(→ *new* key vs. the stale `1.0.0/65536` entries in the repo file).

## 3. Regeneration procedure

**Status 2026-09-02: `tools/paramsets-fetch.js` and the modernized
`tools/paramsets-join.js` are implemented and smoke-tested against the
live CCU (3 keys fetched, joined, validated). Remaining: run the full
fetch against the production CCU (3.87.6, no update planned), join,
validate, commit. Optionally join a second dump from the lab CCU3
(3.89.8) — dedupe by key means it only adds what production lacks.**

1. **New `tools/paramsets-fetch.js`** (Node, uses the existing
   `homematic-xmlrpc` dep; `binrpc` dep for CUxD/BidCos-RF if ever needed —
   BidCos-RF answers XML-RPC on 2001, so xmlrpc suffices for everything
   installed here):

   ```
   node tools/paramsets-fetch.js --host homematic-ccu3 \
        [--ifaces BidCos-RF:2001,HmIP-RF:2010,VirtualDevices:9292/groups,BidCos-Wired:2000] \
        --out ccu_paramsets_dump.json
   ```

   Sketch:
   - per interface: `listDevices` (no init/subscription needed — verified);
     build address→description map; parents carry TYPE/FIRMWARE/VERSION.
   - for every device/channel and every name in its `PARAMSETS`
     (MASTER/VALUES/LINK/SERVICE): compute the cache key with the exact
     `paramsetName()` logic (reuse/extract from ccu-connection.js);
     **dedupe on key** (many same-type devices → one fetch), skip keys already
     fetched this run; `getParamsetDescription(ADDRESS, ps)`.
   - throttle ~150–200 ms/call (matches runtime behavior; CCU is easily
     overloaded); retry once on failure; log progress. Expect a few hundred
     unique keys ≈ minutes.
   - write flat dump JSON, keys sorted.

2. **Modernize `tools/paramsets-join.js`**: take the dump filename as argv
   (default `ccu_paramsets_dump.json`), drop the dead `obj-ease` dep (a
   10-line deep-merge where the dump wins per *paramset key*, i.e. replace the
   whole per-key object — per-parameter deep-merge can leave removed
   parameters behind), sort keys on output, print added/changed/unchanged
   counts. Never delete existing keys (old-firmware users still need them) —
   with one exception: keys proven wrong (none found; see #112 below).

3. **Document** it (tools/README.md or docs/): the two commands above +
   "rerun after every CCU firmware update / before every release touching
   devices" (OQ-5), plus the contribution path: a user's
   `~/.node-red/paramsets.json` is directly join-able — for devices the
   maintainer doesn't own (FCI6 new fw, BBL, DRBLI4, WRCD, BSL 2.0.2, CuxD),
   ask issue reporters to attach that file and merge it with the same tool.
   Add lint exclusion removal for tools/ while at it (scripts are trivial).

4. **Validate**: `node -e "require('./paramsets.json')"`, key-count diff,
   spot-check one HmIP/BidCos/VirtualDevices key, run existing test suite.

Optional later phase: rftypes→description converter for full BidCos coverage
(medium effort, low demand — BidCos is EOL hardware and the runtime
self-heals).

## 5. Effort estimate

- `tools/paramsets-fetch.js` incl. test run against live CCU: **0.5–1 day**
  (reusing paramsetName logic; throttling; dedupe).
- `paramsets-join.js` modernization + docs + lint inclusion: **~2 h**.
- Regeneration run + validation + commit: **~1 h** (production CCU stays
  on 3.87.6 — decided 2026-09-04).
- Issue-specific code work (outside strict B-1 data scope): LEVEL_2 →
  COMBINED_PARAMETER mapping ~0.5–1 day incl. tests; ccu-signal
  OPTICAL_SIGNAL_RECEIVER ~0.5 day; ccu-display WRCD ~1 day; CuxD DIR entry
  ~1 h once a dump exists.
- Community-dump round trips (FCI6/BBL/DRBLI4/WRCD/BSL2/CuxD reporters):
  calendar time, near-zero work each thanks to the join tool.

## 6. Blockers / notes

- No hard blockers: ext4 extraction works on macOS via p7zip; ssh + XML-RPC
  on the CCU verified read-only and light.
- Live CCU runs 3.87.6 vs. image 3.89.8 — the production CCU is **not**
  updated (decided 2026-09-04); paired-device descriptions on 3.87.6 are
  current (see #112 finding in §4). The lab CCUs on 3.89.8 can supply
  group-type keys and act as a diff reference.
- Six of the eight issue devices are not paired on the author's CCU
  (FCI6-new-fw, WRCD, BBL, DRBLI4, BSL-V2, CuxD) → their entries depend on
  reporter dumps; the runtime's self-healing means users are not blocked on
  data, only on the code fixes above.
